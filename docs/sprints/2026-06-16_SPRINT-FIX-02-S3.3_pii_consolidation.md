## 📋 Sekcja A — Business Discovery & Rules

### Stan zastany (dwie implementacje PII)
| Warstwa | API | Recognizery | Używana w |
|---|---|---|---|
| `mcp/pii_*` | **stateful** per-workspace: `anonymize(text, ws)->str`, `deanonymize(text, ws)->str` | `NIP`/`PESEL` (regex 10/11 cyfr, score 0.6), `setup_analyzer` (PERSON/ORG/LOCATION) | **PRODUKCJA**: `api.py`, `swarm/executor.py`, `mcp/server.py` |
| `security/pii/*` | stateless: `anonymize(text)->Result(.text,.mapping)`, `deanonymize(text, mapping)` | `PL_NIP`/`PL_PESEL` (NIP z myślnikami, score 0.8) | tylko własne testy (nigdzie w produkcji) |

Dwie kohabitujące implementacje = ryzyko rozjazdu recognizerów i tokenów (US-FIX-02-3).

### Decyzja (i dlaczego)
> **Kanoniczna = zachowanie produkcyjne (stateful), hostowane w `security/pii/`** (właściwy pakiet
> „security"). `mcp/pii_*` → cienkie shimy re-eksportujące. Powód: nadrzędna zasada
> **NO BEHAVIOR CHANGE 🔴** — produkcja (executor/api/mcp) zależy od API stateful + tokenów
> `<NIP_n>`/`<PERSON_n>`. Przejście na stateless/`PL_NIP` zmieniłoby format tokenów i sygnatury.
>
> **Follow-up (świadomie poza S3.3):** dawny `security/pii` miał *lepszy* recognizer NIP
> (z myślnikami `123-456-78-90`, score 0.8). To realne wzmocnienie detekcji, ale **zmienia
> zachowanie** → wydzielone jako osobny task (nie kasujemy wiedzy — zapisana tutaj i w docstringu
> `security/pii/recognizers.py`).

### ⚖️ Zasady
- **NO BEHAVIOR CHANGE 🔴 (produkcja):** `tests/test_pii_middleware.py`, `tests/security/test_pii_pipeline.py`,
  `tests/test_mcp_pii_integration.py`, `tests/test_pii_recognizers.py` przechodzą **bez zmian asercji**.
- Testy dawnego *stateless* `security/pii` (`test_middleware`, `test_recognizers`) — przepisane na
  API kanoniczne (stary projekt wycofany); zachowują intencję (NIP/PESEL/PERSON + roundtrip + izolacja ws).
